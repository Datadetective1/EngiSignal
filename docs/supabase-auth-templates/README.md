# Supabase Auth email templates

Two EngiSignal emails are **not** sent by this codebase. Supabase sends them,
from templates stored in the Supabase dashboard:

| Template | Triggered by |
|---|---|
| **Confirm signup** | `supabase.auth.signUp(...)` — `app/signin/actions.ts` |
| **Reset Password** | `supabase.auth.resetPasswordForEmail(...)` — `app/signin/actions.ts` |

No other auth template is in use. There is no magic-link, OAuth, change-email or
reauthentication flow in this application, so those templates can be left alone.

The HTML in this folder restyles them to match the rest of EngiSignal's mail. It
was generated by `npm run templates:supabase` from the same design system that
renders the pilot alert and the workspace invitation, so re-running it after a
brand change keeps all four in step.

---

## Do this first: custom SMTP

**This matters more than the templates.** Two things are true of Supabase's
built-in mailer, and both are recorded in the code itself
(`app/signin/actions.ts`, above `requestPasswordResetAction`):

- it is **rate limited**, and not intended for production volume — the exact
  failure the resend-confirmation flow was built to survive, *"a pilot cohort
  that signs up together and meets the hourly email limit"*;
- it sends from **Supabase's domain**, not yours. A customer signing up gets a
  Supabase-branded email, then later an `engisignal.com` one. Restyling the body
  does not fix a sender that says somebody else.

`engisignal.com` is already domain-verified with Resend — confirmed by the DKIM
key at `resend._domainkey.engisignal.com` — so Resend will accept **any** address
on the domain as a sender, `notifications@` included.

### Supabase dashboard steps

1. Dashboard → your EngiSignal project → **Project Settings** → **Authentication**
   (or **Authentication** → **Emails** → **SMTP Settings**).
2. Turn on **Enable Custom SMTP**.
3. Fill in exactly:

| Field | Value |
|---|---|
| Sender email | `notifications@engisignal.com` |
| Sender name | `EngiSignal` |
| Host | `smtp.resend.com` |
| Port | `465` |
| Username | `resend` — the literal word, not an email address |
| Password | your Resend API key |

**On the password:** it is your existing Resend API key — the same value already
in `PILOT_NOTIFY_RESEND_API_KEY`. Copy it from the Resend dashboard or from
Vercel yourself. Do not paste it into this repository, into a chat, or into any
file. Nothing here needs to see it.

**On the port:** 465 is SMTPS with implicit TLS. If your network blocks it, 587
also works and upgrades via STARTTLS. Resend supports 465/2465 (implicit) and
25/587/2587 (STARTTLS).

4. Save, then go to **Authentication** → **Rate Limits** and raise **Rate limit
   for sending emails** — the built-in default is set for the built-in mailer and
   is far below what Resend will accept.
5. Test with a throwaway signup. The confirmation should arrive **from
   `notifications@engisignal.com`**.

### Will `notifications@` actually work?

Yes, on both directions, and it is worth being explicit about why:

- **Outbound** — Resend verifies at the *domain* level, so any mailbox on
  `engisignal.com` is a permitted sender. The DKIM signature is the domain's.
- **Inbound** — `notifications@` is one of the ten Cloudflare Email Routing
  aliases, so a customer who hits reply reaches the operational mailbox rather
  than a black hole. This is the reason it was created as a real alias.

One limitation to accept: **Supabase templates have no `Reply-To` field.** Replies
to auth email will land on `notifications@`. That is fine — it forwards — but it
is why the emails this codebase sends set `Reply-To` explicitly and these two
cannot.

## Read this before pasting

**The templates were not edited from code, and the link expression is not
supplied.** Both files contain the sentinel `{{LINK}}` where the URL belongs.

That is deliberate. `lib/auth/origin.ts` points confirmation mail at
`/auth/confirm` — a two-step page — rather than at the token-consuming callback,
because the PKCE code verifier lives in a cookie in whichever browser started
sign-up, and email links are routinely opened somewhere else. Production logs
showed that failing as `bad_code_verifier`. A guessed URL here would break
sign-up for everybody, which is exactly the risk you flagged when you left these
templates alone the first time.

So: **keep the href that is already working, and change only what is around it.**

## Confirm signup

1. Open the Supabase dashboard → your EngiSignal project.
2. **Authentication** → **Emails** → **Templates** tab.
3. Select **Confirm signup**.
4. **Copy the entire existing template body into a scratch file first.** This is
   your rollback, and there is no version history on these.
5. In that copy, find the `href="..."` on the confirmation link and copy the URL
   expression out of it. It will look something like
   `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup&next=/app`.
6. Open [`confirm-signup.html`](confirm-signup.html), replace the single
   occurrence of `{{LINK}}` with the expression from step 5, and paste the whole
   thing into the template body.
7. Leave the **Subject heading** as it is unless you want to change it. If you do,
   `Confirm your EngiSignal account` matches the new body.
8. **Save**.
9. Sign up with a throwaway address and confirm that the email arrives, looks
   right, and that clicking through signs you in.

## Reset Password

Same steps, against the **Reset Password** template and
[`reset-password.html`](reset-password.html). Its existing href is usually
`{{ .ConfirmationURL }}`; whatever it is, carry it across unchanged.

Verify by using **Forgot password** on the sign-in page with a throwaway account.

## The plain-text part

Supabase sends only the HTML body — there is no separate text field in the
dashboard. `confirm-signup.txt` and `reset-password.txt` are provided so the
wording has a reviewed plain-text form if Supabase ever adds one, and so the
copy can be read without rendering HTML. Nothing needs pasting from them today.

This is a real gap and it is Supabase's, not ours: the two emails this codebase
sends itself (pilot alert, workspace invitation) both carry a proper text
alternative.

## A separate change you may want, but should not bundle with this one

`MULTI_USER_RELEASE.md` records that the **Confirm signup** link has `next=/app`
hard-coded. That means an invited user who signs up from an invitation link
lands on `/app` rather than on their invitation, and has to reach it via
`/invitations`. Both paths work; the second is tidier.

The fix is to change the href to:

```
{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=signup
```

`{{ .RedirectTo }}` already carries `/auth/confirm?next=<destination>`, because
`emailConfirmUrl()` builds it that way, so appending the token parameters with
`&` produces the correct URL.

**Do it as its own change, after the restyle is confirmed working.** If you
change the layout and the routing together and sign-up breaks, you will not know
which one did it. Test it by accepting a real invitation end to end, not just by
signing up.

---

## What this does not change

Nothing about authentication behaviour, token lifetimes, single-use semantics,
redirect validation or invitation routing. These files are presentation only,
and the one expression that controls where a link goes is the one this folder
deliberately refuses to supply.
